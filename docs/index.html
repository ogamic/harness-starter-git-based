Sound familiar?

Coding agents are good at the task in front of them. What breaks is everything around it.

  • You come back after three weeks, and nobody — not you, not the agent — remembers why it was built this way.
  • You asked an agent to plan. It also rewrote the code, past the conventions that part of the codebase follows.
  • An agent went ahead on a call that was yours to make.
  • The agent says done. Nothing proves it.
  • Your Claude Code setup and your Codex setup quietly say different things.

These are team problems, and they show up on day one even when you work alone: you-in-three-weeks is a teammate with no memory. Each idea below answers one of them.

Your harness runs the agents. Gangline runs the work.

Claude Code and Codex can already run many agents at once: subagents, parallel sessions. What they don't give you is the team around them. Who plans and who builds. Which calls wait for you. What counts as done. Where the decision from three weeks ago is written down.

Gangline keeps those answers as files in your repo. Each role is generated into every tool's own subagents (skills in Antigravity), and the board records every ticket, decision and result. Switch tools, close the session, come back in a month, and the team is still there.

It isn't a framework you install into a codebase, a persona theater that role-plays an agile team, or a catalog of subagent parts. It doesn't replace your harness's agents. It decides who does what, what waits for you, and what counts as done.

Four ideas, all in plain files

01

A PM agent that never codes

One agent coordinates. It discusses intent, scopes work into tickets, and delegates to domain sub-agents, one per surface. It never edits source, and each sub-agent carries its own conventions.

Answers: the planner that also rewrote the code.
02

An org chart for agents

Sub-agents execute; you gate the decisions that are really yours. Who may act without asking, and what counts as done, is written down, versioned and reviewable.

Answers: the agent that made your call · “done” with no proof.
03

A board that's just files

Tickets, bugs and decisions are numbered markdown files, indexed by a STATUS.md you can read in any editor. No database, no service, no account. git is the whole backend.

Answers: nobody remembering why.
04

One definition, every harness

Roles and skills are written once and generated into Claude Code, Codex and Antigravity config. Switch tools, or run two at once in separate worktrees, without rewriting your org chart.

Answers: two setups that quietly drift apart.

How it works

You talk to one agent, launched in management/. Everything it does leaves a file behind.

  1. You state the intent

    "Users should be able to export their data." The PM discusses, investigates and drafts a plan.

  2. The PM searches the board

    It checks STATUS.md for related work and extends an existing ticket rather than opening a duplicate.

  3. The autonomy rubric decides

    Four signals: blast radius, change type, product decision, contract. All clear, and it starts. Any fails, and it waits for your go.

  4. A ticket file becomes the spec

    It writes backlog/NNNN-slug.md, adds the row to STATUS.md, and hands the file to the owning sub-agent.

  5. Done means evidence

    Build and tests with counts, behavior observed where it runs, and a harness delta: what this ticket taught the system.

Write a role once. Every harness loads it.

A small, dependency-free Node script fans your roles and skills out to each tool's own format. The output is committed, so you can review exactly what each harness will load.

Start with files. Graduate when a team shows up.

This starter

Free and fully open. One person, one machine. The board is markdown in git, with nothing to host and no account to create.

Musher in early testing

The team version, for when a second person, parallel agents or a need for permissions shows up. It's still an experiment. The playbook, rubric and sub-agents are meant to stay the same; only where the board lives changes.
